## Why the kernel variant fails at B = 8

* **O1 at B = 8 alone needs about 19.5 GiB.** An O1-only file (O2 + O1 templates, the data of cert_SLSRSRSR, `checkO1 cert prog o1Data =
  true := by decide +kernel`) passes with plain `lean` (no Mathlib) in 171 s at a peak of **19.45 GiB**. The same file with the four
  Mathlib imports of the U(1) source is killed after 131.5 s at 20.0 GiB. The kernel keeps every intermediate term of one declaration in its
  `whnf` cache until that declaration is checked (design doc §7). At B = 8 the O1 checker builds the supertile (2584 triangles per type), the
  owned rhombs and the edge table, and runs the turtle. The cost depends on B, much less on the certificate, which is why all the kills
  happen at about the same time.
* **The U(1) file adds about 2 GiB on top.** With O1 by `native_decide`, B = 6 files peak at 1.9–2.3 GiB (Mathlib modules, the ~230
  theorems of the soundness part, the other checks). B = 6 with O1 in the kernel peaks at 4.2–4.4 GiB. So a B = 8 U(1) file needs about
  21–22 GiB with kernel O1, just above the limit.
* **Not parallelism.** The command-line Lean 4.30 front end turns `Elab.async` on by default (`Lean/Elab/Frontend.lean`), so the four
  checks could be elaborated in parallel and their caches add up. But with `-DElab.async=false` (checks one after the other)
  cert_SLSRSRSR is killed in the same way (190.1 s, 19.61 GiB), so the cause is O1 alone.
* The largest native-O1 run (cert_SRSRSRSRSSR, 238 s, 16.4 GiB) is dominated by O4/O6 (`checkO46`, 160 s / 15 GB on its own) and O2/O3
  (95 s). It stays below the limit.

## Remedy for a kernel-only Theorem U(1) at B = 8 (not done here)

Split O1 into separate theorems, each under 20 GiB, for example one per pass family of parity B mod 2 (`checkPassO1 ix tbls prog p = true`
for each `p ∈ o1Data`, plus `coversBase`). Then assemble them into `checkO1 cert prog o1Data = true` by a lemma about `List.all`, so that
the final theorem and its axioms stay unchanged. The kernel cache is released after each declaration, so the peak is that of the largest
part. Check first which part dominates. The edge tables of the supertile of level B (`buildTable col sign B : Option Nav`) are shared by all
pass families of a type, so if each part rebuilds them it repeats that cost. A split that is worth it probably proves the table of each
type once (for example `buildTable col sign B = some tbl` with the table as certificate data, checked in its own theorem) and then runs the
passes against it.
