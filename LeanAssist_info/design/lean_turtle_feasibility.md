# Lean 支援証明を turtle_boundedness の証明に適用する可能性 (考察)

作成: 2026-10-16 (LeanAssist v1.0 と同時)。対象: turtle_boundedness (公開版 [transreal/pt_turtle](https://github.com/transreal/pt_turtle)) の
2 つの定理 — ペンローズ菱形タイル張り上のタートル・プログラムの **有界性** (定理 3/4: 59 プログラム) と **非有界性** (定理 5/6: 18 プログラム) — および関連パッケージ (CellularAutomata.wl / TurtleTiling.wl / BlockingNimCA.wl) の計算結果。

## 1. 現状の信頼基盤

現在の証明は「数学的議論 (proof_sketch.md, proof_unbounded.md)」と「有限の計算的検査」からなる。計算部分は 3 系統の独立実装 (Python numpy/CUDA、独立に書かれた `indep_check.py`、Wolfram Language `lib.wl` / `TurtleTiling.wl`) が一致することで信頼されている。これは「多数決による信頼」であり、

* 3 実装が **同じ仕様の読み違い** を共有していれば検出できない、
* 実装の正しさと数学的議論の正しさ (帰納法・補題の適用条件) が別々に査読されている、

という弱点がある。Lean を入れる目的は、(a) 有限検査を **カーネル検証された 1 本の検査器**に置き換えること、(b) 数学的議論のうち **組合せ的・帰納的な骨格**を形式化して、残る「信頼する命題」を明示的な公理 (axiom) の短いリストにすることである。

## 4. CellularAutomata / BlockingNimCA 側の結果

* `BNMassConservedQ` (質量・重心の保存) は WL では `Expand[...] === 0` による多項式恒等式の証明。Lean では `if v < 0 then v + k else v` を含む整数恒等式として書き、定義を展開した後は `omega` だけで (Mathlib 無し、公理 propext/Quot.sound のみで) 検証できる — 実測済み (作例ノートブック §5)。一般オフセット (α, β, γ) と仮定 γ = 3(β − α) 付きの版も同じ。誤った規則 {1,2,4} では Lean が拒否する。
* `BNSymbolicEvolve` の「p ≥ P で全セルが一次式」という主張は Presburger 算術の範囲 (区分線形 + 整数) なので、ステップごとの主張は `omega` で検証できる。帰納法の骨格を Lean に書けば「全ての整数 p について」の定理になる。
* `IsReversiblePCA5` のような有限規則表の性質は `decide` で検証できる (LeanDataDefinitions で規則表を書き出す)。
* `TurtleTiling.wl` の navigation (`BuildTurtleNav`) と `lib.wl` の `ptNav` は同じ仕様 (辺キーの一致) なので、Lean 側の定義を 1 本書けば `wl_verify.wl` の独立検証を Lean 検証に置き換えられる。

## 5. 作業方式 (LeanAssist が提供するもの)

1. **Mathematica が証明書を計算し、Lean が検査する**: 多項式恒等式は Groebner 基底で `linear_combination` の係数を求め (`LeanPolynomialCertificate`)、Lean 側は `ring` で確認するだけにする。有限証明書は `LeanDataDefinitions` で Lean の `def` として書き出し、`decide` で検査する。
2. **Lean の診断を構造化して受け取る**: LeanLink の `LeanImportString` はエラー本文も `sorry` も報告しない。`LeanCheck` は `lean` を直接呼び、エラー・警告・`#print axioms` を解析して `sorryAx` / `Lean.ofReduceBool` の有無を必ず表示する。「Proved」は *エラー無し・sorry 無し* の意味。
3. **反例テスト**: 証明書を 1 か所壊して Lean が拒否することを確認する (`LeanTurtlePortIdentities[..., "Perturb" -> {portId, "delta", 1}]`)。検査器が空虚でないことの最低限の保証。
4. **Mathlib 版と素の Lean 版の使い分け**: 実数・`ring`・`linear_combination` は Mathlib (コンパイル約 10 s)、整数算術と `decide` は素の Lean (1 s 未満)。証明書検査は後者に寄せる。

## 7. 制約と注意

* Wolfram/LeanLink 1.0.9 は Lean v4.30.0 に固定 (シムの ABI)。Mathlib もそれに合わせた版 (`~/src/mathlib4`, rev v4.30.0)。Lean/Mathlib を上げるときは LeanLink のシムを再ビルドする必要がある。
* `native_decide` を使った定理は `#print axioms` に補助公理が出る (Lean v4.30 では `<定理名>._native.native_decide.ax_1_1`、古い版では `Lean.ofReduceBool`)。論文で「Lean で検証した」と書くときは、カーネル検証 (`decide`) か コンパイラ信頼 (`native_decide`) かを区別して書く。
* O1 の kernel 検査の性能の要点: 辺の探索を線形探索にすると 444 回の S 移動 × 756 辺の Z5 比較で kernel には重い。座標を 1 つの `Nat` に詰めたキー (GMP 加速の比較 1 回) と平衡二分探索木 (深さ ≤ 10) で 27 s。整列・木の構築は燃料付きの構造的再帰で書く (整礎再帰の定義は kernel で簡約できない)。
* `decide +kernel` のメモリは「生きているデータ」ではなく「簡約の総量」に比例する: kernel の `whnf`/`whnf_core` は 1 つの宣言の検査が終わるまで途中の項をすべてキャッシュに残す (O1 の 5 分で 18 GB、旧 O46 で 41 GB)。前のレベルを捨てる畳み込みにしてもそれだけでは減らない。効くのは (1) 不変な計算 (族の絞り込み・整列・表) をループの外へ出すこと、(2) 内側のループを再帰子 (`BTree.rec`/`List.rec`) と原始演算 (`Nat.ble`/`Nat.beq`/`Nat.add`、`Bool.rec`) で書くこと (構造的再帰は `brecOn` と `PProd` の below を、`if` は `Decidable` 経由の簡約を毎回作るので約 4 倍)。再帰子の定義はコード生成できないので、同じ分岐の構造的再帰の双子を書いて `@[csimp] theorem f = fImpl` で等しさを証明すれば `native_decide`/`#eval` も使える (`noncomputable def f` でも、`f` を参照する計算可能な定義は csimp 置換でコンパイルされる)。`show` で `Bool.rec` を書くときは `(motive := fun _ => Nat)` を明示する (無いと "failed to elaborate eliminator")。メモリの測定は lean.exe を直接 `-M` 付きで走らせ、作業集合を監視して上限で kill する (Python の psutil で 0.25 s ごとに見て `taskkill /T /F`。`-M` が kernel の簡約を止めるかは未確認)。
* `LeanCheckFile` は `#print axioms` をファイル末尾に付け足すので、`namespace ... end` で囲んだ定理は名前が解決できない。修飾名 (`theorem AffineRecurrence.affine_unique`) で宣言する。
* `variable (S : PassSystem _)` の下の再帰定義では、本体の再帰呼び出しに `S.trace` のような field notation が使えない (section 変数は固定引数として既に適用済み): `trace X c k` と書く。
* Mathlib のモジュールを絞って import すると型クラスのインスタンスが見えないことがある (`AddGroup ℤ` は `Mathlib.Algebra.Group.Int.Defs`)。`le_rfl`・`Nat.le_induction` も `Mathlib.Algebra.Group.Basic` だけでは見えないので、`Nat.le_refl`・自前の帰納法で書いた。
* `decide +kernel` が偽を返したときの Lean のエラーは、大きなデータを含む命題の表示で `maximum recursion depth` になることがある。Status は Failed なので判定には影響しない。
* `linear_combination` 証明は定理の仮定に **非退化条件** (`c2 ≠ 0` など) が必要になることが多い。LeanAssist は証明書に使った因子だけを仮定として定理に載せるので、Lean の定理文がそのまま「実際に証明された主張」になる。
* 大きなデータを Lean のリストリテラル (数千要素の `List Nat`) で書くと、`native_decide` 以前に各 `def` のコンパイル (IR 生成) が遅い: V(SSR, 7) の証明書 (2.8 MB) で 607 s・11.8 GB。256 個ずつ 1 つの大きな Nat (16 進リテラル、桁幅はチャンクの最大ビット長) に詰め、Lean 側で `%` と `/` で開く (`TurtleBounded.unpack`; kernel でもコンパイル済みコードでも GMP) と 16 s・0.4 GB、ファイルも 1.8 MB。
* kernel での燃料付き merge sort (`BTree.ofList`) は 3276 件で 17 s かかる (簡約の総量が大きい)。整列は証明書側 (Mathematica) で行い、Lean は計算したキーが狭義単調であることを確かめて一度で平衡木を組む (`treeOfSorted`/`buildBal`、0.8 s)。要素の抜けは探索の失敗になるだけなので安全側。
* 同じファイルの定理は Lean v4.30 の既定では並列に検査される (メモリが足し算になる)。kernel の重い定理を並べるときは `set_option Elab.async false` で 1 つずつにする (メモリは定理ごとに解放される: V(SSR, 7) の 30 定理でピーク 6.8 GB)。
* 構造体インスタンス `{ a := x,` の次の行のフィールドが 1 つ目のフィールドより左にあると `unexpected identifier; expected '}'` になる。生成するデータは 1 行に書く。
* `set_option profiler true` の "type checking took" には、直前のデータ `def` の検査などで約 4 s の基底が乗る (`Nat.blt 0 1` でも 4 s)。小さな計測は差で読む。
* 自分の名前空間に `Quad.wInRange` を定義しても `q.wInRange` (q : `TurtleO1.Quad`) は `TurtleO1.Quad.wInRange` を探して失敗する。`Quad.wInRange q` と明示する。
* 作業集合 (psutil の rss / peak_wset) で上限を見るときは、マシンのメモリが逼迫すると Windows が作業集合を削る (ページング) ので、ピークが実際の必要量より小さく出て時間が延びる (2026-10-16 夜: llama-server.exe が private 28 GiB を持ち空きが 15 GiB のとき、B = 8 の U(1) が 19.1 GiB・409 s で通った。同じ検査は普段 20 GiB を超えて kill)。開始時の空きメモリを記録し、上限より少なければ待つか止める。B = 8 の O1 の `decide +kernel` は単独でも 19.45 GiB (Mathlib 無し、171 s) で、Mathlib のモジュールを import するだけで 20 GiB を超える。
